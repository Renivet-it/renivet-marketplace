# REN-225 Engineering Specification

## Scope and outcome

**Linear:** REN-225 — `[FCCP][P1] Invoice-Numbering & Commission-Percentage Canonical Source (BIZ-6a / BIZ-6b)`  
**Branch:** `feat/ren-203-spec` (the Linear issue's suggested branch is different; this specification follows the user's explicit same-branch request)  
**Risk:** L3 — financial reporting, customer/legal invoice identity, and historical-data compatibility

REN-225 has two independent deliverables:

1. Make every marketplace commission-percentage display/export derive from the resolved `commission_rules` rate, without changing rate resolution or payout calculation.
2. Make the existing storefront order `invoice_number` the single customer/legal invoice number for new orders, generated by a unique professional non-predictable generator, and make all other identifiers explicit references.

The cutover is forward-only. Existing populated invoice numbers remain valid historical values; no historical order is regenerated or backfilled by this task.

## Repository evidence

- `src/lib/order-invoice.ts` currently issues `BRANDCODE/FY/00001` values from a per-brand financial-year sequence. This is unique but exposes brand, financial year, and order issuance sequence.
- `src/lib/db/schema/order.ts` already has the unique nullable `orders.invoice_number` field and `invoice_issued_at`; the `brand_invoice_sequences` table supports the current scheme.
- `src/lib/finance/gst.ts` currently creates marketplace GST export invoice values with `formatInvoiceNumber("INV", order.id, monthKey)`, which derives a synthetic value from month and order ID rather than the stored authoritative invoice number. Refund rows similarly derive synthetic credit-note values.
- `src/app/api/invoices/[orderId]/download/route.tsx` and `src/app/api/delhivery/invoice/route.tsx` already consume the order's stored invoice number.
- `src/components/pdf/invoice-template.tsx` falls back from the stored invoice number to `receiptId` or `id`; the fallback must be classified as a reference or be prevented for a legal invoice path.
- Marketplace payout summaries resolve `commissionPercentBps` from `commission_rules` through `src/lib/finance/payouts.ts` and `src/lib/finance/payout-commission.ts`.
- Corporate settlement statements persist `commissionPercentBps` from the agreed corporate order amount and render it in settlement documents. This is a separate corporate commercial-document domain and must not be silently relabeled as the marketplace `commission_rules` rate.
- Dashboard/category and legacy monthly-compliance displays contain additional commission-rate presentation logic and must be audited during implementation for whether they are marketplace `commission_rules` views or separate historical/corporate values.

## Approved business rules

- **BIZ-6(a):** one canonical commission-percentage source/field is authoritative. Display and export labels may differ for presentation, but must derive from that source rather than an independently maintained value.
- **BIZ-6(b):** one authoritative customer-facing/legal invoice number is used. Order reference, export reference, settlement reference, and internal IDs remain usable only when explicitly labeled as references.
- New invoice numbers must be unique, professional, non-predictable, and non-trivially decodable. The implementation must document its format and entropy/collision strategy.
- Historical invoice numbers are not changed, regenerated, or backfilled.
- Legacy document/export reads must continue to work for historical orders that have only their old-format value.
- Commission rate value resolution, bps conversion, payout calculation, and execution controls remain outside this task.

## Proposed design

### Commission source boundary

Create or reuse a single pure read/format boundary for the marketplace commission rate:

- input: the resolved `commission_rules` winner/rate in basis points;
- output: the display/export percentage derived only from that rate;
- no second persisted percentage label and no conversion from a commission amount for marketplace surfaces;
- unconfigured brands/categories render an explicit unconfigured state rather than a guessed zero or a stale label.

Inventory every commission percentage consumer found by repository search. Route marketplace payout, finance, order/admin, and export surfaces through the canonical boundary. Preserve corporate settlement snapshots where they are legally/commercially order-specific, but label them as the corporate settlement commission rate and document that they are not a competing marketplace `commission_rules` source. Any requirement to make corporate rates also derive from marketplace rules would be a separate business decision because the current corporate domain persists agreed order-specific terms.

### Invoice-number boundary

Keep `orders.invoice_number` as the authoritative customer/legal field. Replace only the new-order generation algorithm at the existing `ensureOrderInvoiceNumber` issuance boundary. The recommended format is a fixed `INV-` prefix plus a cryptographically random, uppercase, human-safe token (for example, grouped base32 characters), with uniqueness enforced by the existing database unique index and retry on collision. It must not encode order ID, row position, brand, or timestamp. The exact alphabet, length, and retry behavior must be documented in implementation tests and the PR.

The generator must be transaction-safe and idempotent:

- lock/read the order first;
- return an existing invoice number unchanged;
- generate and persist only when the field is empty;
- rely on the database uniqueness constraint and bounded collision retry;
- preserve `invoice_issued_at` semantics.

Update all customer/legal invoice documents and GST exports to read `orders.invoice_number`. Keep order IDs, receipt IDs, public order IDs, refund IDs, and synthetic export references in separately named reference columns/labels. For historical orders, use the stored old invoice number unchanged; if a legacy row has no invoice number, the export/document path must fail clearly or use a separately labeled non-invoice reference rather than silently minting a legal invoice number.

No migration is required to rewrite existing values. If a schema or index adjustment is required for the generator, it must be additive and must not mutate historical rows.

## Requirements

- `REQ-225-001`: All marketplace commission-percentage display/export paths derive from the resolved `commission_rules` rate through one canonical formatting/read boundary.
- `REQ-225-002`: REN-225 does not alter commission-rate resolution, bps calculation, payout amount calculation, or payout execution behavior.
- `REQ-225-003`: New storefront orders receive one unique authoritative customer/legal invoice number in `orders.invoice_number` through a transaction-safe, idempotent, non-predictable generator.
- `REQ-225-004`: The invoice format does not directly encode order ID, row index, brand, or reversible creation timestamp, and collision handling is fail-safe.
- `REQ-225-005`: Customer-facing/legal documents and GST exports use the authoritative stored invoice number; other identifiers are explicitly labeled references.
- `REQ-225-006`: Historical invoice values remain unchanged, and historical orders with only old-format values continue to render/export without silent regeneration.
- `REQ-225-007`: The forward-only cutover boundary and legacy compatibility behavior are documented in code/tests and the implementation PR.
- `REQ-225-008`: Authorization, auditability, and failure handling prevent an untrusted client from supplying or replacing an invoice number or commission percentage.

## Scenarios

- `SCN-225-001`: A configured marketplace brand/category displays and exports the exact percentage derived from its resolved `commission_rules` basis-point value.
- `SCN-225-002`: An unconfigured marketplace scope renders an explicit unconfigured state and never falls back to a stale independently stored label.
- `SCN-225-003`: Corporate settlement documents preserve their order-specific agreed rate and label it as a corporate settlement value rather than treating it as a marketplace `commission_rules` label.
- `SCN-225-004`: A new order receives an invoice number once, concurrent issuance returns the same value, and no duplicate value can be committed.
- `SCN-225-005`: Generated invoice numbers conform to the documented format and do not expose a reversible order identifier, sequence, brand, or timestamp.
- `SCN-225-006`: Customer invoice PDF, delivery invoice flow, order/admin display, and GST export all use the stored authoritative invoice number and classify order/export IDs as references.
- `SCN-225-007`: A historical order with an old invoice number is rendered/exported unchanged; no backfill occurs.
- `SCN-225-008`: A historical order without an invoice number is handled explicitly without minting a number during read/export and produces a bounded actionable error or labeled reference.
- `SCN-225-009`: A uniqueness collision or persistence failure does not return a false invoice, overwrite another order, or leave a partially issued legal number.
- `SCN-225-010`: A client cannot submit a custom invoice number or commission percentage to alter the authoritative values.

## Invariants

- `INV-225-001`: One order has at most one immutable-after-issuance authoritative invoice number.
- `INV-225-002`: No customer/legal invoice surface presents an order ID, receipt ID, export synthetic value, or settlement reference as the invoice number.
- `INV-225-003`: Marketplace commission percentage labels are a pure representation of the resolved `commission_rules` basis-point value.
- `INV-225-004`: REN-225 cannot change a historical invoice number or create one as a read-side side effect.
- `INV-225-005`: Invoice issuance is idempotent under retries and safe under concurrent requests.
- `INV-225-006`: Failed generation/persistence fails closed and never substitutes a predictable or client-supplied value.
- `INV-225-007`: Corporate order-specific commission snapshots remain separate from marketplace commission-rule resolution unless a separately approved business decision changes that boundary.

## Flows

- `FLOW-225-001`: Resolve marketplace commission rule -> canonical bps-to-percent presentation -> display/export.
- `FLOW-225-002`: New order invoice request -> transaction lock/existing-value check -> secure generation -> unique persistence -> document/export consumption.
- `FLOW-225-003`: Historical document/export read -> stored legacy invoice value or explicit missing-value handling -> labeled reference fields.
- `FLOW-225-004`: Concurrent issuance/retry -> idempotent existing-value return or bounded collision retry -> fail closed.

## Dependencies and integrations

- `DEP-225-001`: REN-203/REN-209 `commission_rules` resolution; consumed as the source, not reimplemented.
- `DEP-225-002`: Existing `orders.invoice_number` and unique index; the authoritative field and collision boundary.
- `DEP-225-003`: Existing order invoice issuance, download, shipping, PDF, and finance export paths.
- `DEP-225-004`: Corporate document/settlement model; retained as a separate order-specific commercial domain.
- `DEP-225-005`: Existing historical data with approximately eight populated legacy invoice values and orders with no value.

- `INT-225-001`: Database transaction and uniqueness constraint — collision or transaction failure must fail closed and be retry-safe.
- `INT-225-002`: GST export — must use stored invoice number and keep order/export references in explicit reference fields.
- `INT-225-003`: Customer/legal PDF and delivery provider invoice paths — must consume only the authoritative invoice field.
- `INT-225-004`: Admin/customer/brand document views — must distinguish invoice numbers from references.

## Security and authorization boundaries

- `SEC-225-001`: Only trusted server-side issuance code may create an invoice number; clients cannot provide or overwrite it.
- `SEC-225-002`: Random invoice tokens must not expose order identity, customer identity, brand identity, or timing information.
- `SEC-225-003`: Export and document APIs must preserve existing authorization and must not expose internal identifiers under an invoice label.
- `SEC-225-004`: Commission labels must not be writable presentation data supplied by a client or independently editable admin field.

## Decisions

- `DEC-225-001` — **Resolved / AUTO_DECIDE:** Keep `orders.invoice_number` as the authoritative field because it is already unique, consumed by customer invoice APIs, and is the field named by the issue.
- `DEC-225-002` — **Resolved / RECOMMEND_CONTINUE:** Use a cryptographically random fixed-format token under an `INV-` prefix rather than a new sequential or timestamp-derived format. Basis: satisfies non-predictability and avoids exposing internal identity; uniqueness remains database-enforced.
- `DEC-225-003` — **Resolved / RECOMMEND_CONTINUE:** Do not force corporate order-specific settlement commission snapshots through marketplace `commission_rules`; preserve their legal/commercial snapshot semantics and label their source explicitly. Basis: current corporate orders persist agreed terms separately and the issue says the two decisions must not be merged.
- `DEC-225-004` — **Resolved / AUTO_DECIDE:** Use a forward-only cutover with no data migration/backfill. Basis: explicit acceptance and production-safety gate in REN-225.

## Validation plan

- Unit tests for canonical commission formatting, configured/unconfigured states, and exact bps-to-percent conversion.
- Repository consumer tests proving no marketplace display/export path keeps an independent commission percentage.
- Unit tests for invoice format, entropy/absence of reversible order mapping, uniqueness, and bounded collision retry.
- Concurrency/idempotency integration tests for two issuance attempts on one order and two orders under a forced token collision.
- Document/export integration tests for stored new-format and legacy-format values, including missing-value handling.
- Regression tests proving REN-203 commission amounts and payout behavior are unchanged.
- Authorization/security tests proving client input cannot override invoice or commission values.
- Business UAT: sample new orders with a configured brand (Terra Luna) and an unconfigured brand/scope; verify displayed percentage source and invoice/reference labels.

## Explicit exclusions

- No historical invoice renumbering or backfill.
- No change to commission rate selection, rate value, bps conversion, payout amount, holdback, eligibility, or payout execution.
- No change to corporate tax-invoice numbering, brand supplier invoice numbering, proforma numbering, or settlement statement numbering except classification/labeling where those documents surface references.
- No production order creation, invoice issuance, export submission, payout, or data mutation during specification work.
