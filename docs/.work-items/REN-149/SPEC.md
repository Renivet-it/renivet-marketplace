# REN-149 Engineering Specification

## Title

Reconnect the search bar's intent-classification redirect

## Status

READY_FOR_DEV — explicitly approved by Ayan Ganguly on 2026-09-09.

## Scope and outcome

The search mutation already returns a `redirectUrl` generated by `getSearchRedirectUrl()` from the classified search result. The `ProductSearch` client currently ignores that field and always calls `navigateToCatalogWithSearch(result.originalQuery)`. The implementation will make the success handler navigate to the returned redirect URL while preserving the current generic-search fallback on mutation errors and for UNKNOWN intent.

In scope:

- The `processSearchMutation.onSuccess` consumer in `src/components/ui/product-search.tsx`.
- A small navigation helper or equivalent testable boundary, if needed to preserve loading-state and current-url behavior.
- Targeted automated coverage for brand, category-family, and unknown redirect outcomes.
- Manual verification of actual destination paths.

Out of scope:

- Changes to intent classification, confidence thresholds, database queries, search analytics schema, or `getSearchRedirectUrl()` unless investigation proves the returned contract is invalid.
- Typeahead suggestions.
- The separate shop facet-count/filter alignment defect.

## Repository evidence

- `src/lib/trpc/routes/general/search.ts` returns `redirectUrl: getSearchRedirectUrl(result)` from `processSearch`.
- `src/lib/search/search-engine.ts` maps BRAND to `/brands/{slug}`, CATEGORY to `/shop?categoryId=...`, SUBCATEGORY to `/shop?subcategoryId=...`, PRODUCT_TYPE to `/shop?productTypeId=...`, and UNKNOWN to `/shop?search=...`.
- `src/components/ui/product-search.tsx` currently calls `navigateToCatalogWithSearch(result.originalQuery)` in `onSuccess`.
- The mutation error handler already preserves the generic query navigation behavior.
- The current checkout/SEO working tree contains unrelated user changes; implementation must start from an appropriate task branch and must not overwrite them.

## Risk assessment

Final risk: L2.

The code change is small and reversible, but it crosses a server-returned routing contract and a customer-facing navigation boundary. Incorrect handling could send users to the wrong brand/category page or regress generic search. No authentication, payment, order state, schema, or destructive operation is involved.

## Requirements

- REQ-149-001: Successful search submissions must use the server-returned `redirectUrl` as the destination.
- REQ-149-002: BRAND results must land at the returned `/brands/{slug}` destination.
- REQ-149-003: CATEGORY, SUBCATEGORY, and PRODUCT_TYPE results must land at their returned pre-filtered `/shop` destination.
- REQ-149-004: UNKNOWN results must retain the existing generic `/shop?search=...` behavior.
- REQ-149-005: Search mutation errors must retain the existing local-query fallback behavior.
- REQ-149-006: Existing loading, sheet-closing, current-URL short-circuit, and navigation behavior must remain intact where applicable.
- REQ-149-007: No client-provided identity or analytics contract must be added or changed.

## Scenarios

- SCN-149-001: A known brand search returns a brand redirect and the browser navigates to that brand path.
- SCN-149-002: A known category, subcategory, or product-type search returns a filtered shop redirect and the browser navigates to it.
- SCN-149-003: An unknown/free-text search returns the generic search redirect and the browser navigates to `/shop?search=...`.
- SCN-149-004: The search mutation fails and the browser uses the submitted query through the existing fallback.
- SCN-149-005: A successful redirect closes suggestions/sheet and does not leave the search loader stuck; an already-current destination remains short-circuited according to existing behavior.

## Invariants

- INV-149-001: The client does not reconstruct or override a valid server-provided intent destination.
- INV-149-002: A failed analytics/search request cannot prevent the existing fallback navigation.
- INV-149-003: Search navigation does not trust or transmit customer identity from the browser.
- INV-149-004: A search submission produces at most one navigation attempt.

## Flow

- FLOW-149-001: Submit query -> process search mutation -> close search UI -> navigate to `result.redirectUrl`.
- FLOW-149-002: Mutation failure -> close search UI -> navigate using the submitted query through the existing generic helper.
- FLOW-149-003: UNKNOWN classification -> server-generated generic redirect -> existing generic shop search destination.

## Dependencies and integrations

- DEP-149-001: `general.search.processSearch` must continue returning a non-empty `redirectUrl` for every successful result. Status: existing/resolved.
- DEP-149-002: Destination routes `/brands/[slug]` and `/shop` must continue accepting the URL forms generated by `getSearchRedirectUrl()`. Status: existing, manual verification required.
- INT-149-001: Search intent classifier and redirect helper. Failure behavior: client preserves existing generic fallback only when the mutation fails; it must not silently replace a successful redirect with the raw query. Status: existing.

## Personas and boundaries

- PER-149-001: Customer searching for a brand, category, product type, or free-text term.
- SEC-149-001: The browser receives routing data only; authentication and analytics persistence remain governed by the existing server procedure and are unchanged.

## Decisions

- DEC-149-001: Reuse the existing `redirectUrl` returned by the server rather than duplicating classification logic in the client. Class A / AUTO_DECIDE; this is the existing authoritative contract and minimizes divergence.
- DEC-149-002: Keep `navigateToCatalogWithSearch()` for raw-query fallback and empty-search behavior; add only the smallest equivalent direct-navigation path needed for server-provided URLs. Class B / RECOMMEND_CONTINUE; this preserves existing query cleanup semantics while avoiding accidental rewriting of brand URLs.

## Test expectations

- TEXP-149-001: Unit/component test verifies BRAND success uses `redirectUrl` and does not call the raw-query navigation path. Category-family variants are covered by representative returned URLs. Category: component; REQUIRED.
- TEXP-149-002: Component test verifies UNKNOWN success reaches the existing generic `/shop?search=` destination. Category: regression; REQUIRED.
- TEXP-149-003: Component test verifies mutation errors use the submitted-query fallback. Category: regression; REQUIRED.
- TEXP-149-004: Manual QA verifies a real known-brand search, category search, product-type search, and unknown search land at the expected paths, with loading/sheet behavior intact. Category: ui_ux; REQUIRED.
- TEXP-149-005: Regression verification confirms search analytics request shape and server-side identity boundary are unchanged. Category: integration; REQUIRED.
