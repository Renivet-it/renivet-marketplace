# Cross-Project Critique — P01, P02, P05, P06, P08

Independent adversarial pass over the five just-completed Epic packages (`projects/P01-search-ranking/`, `P02-recommendations/`, `P05-customer-journey/`, `P06-measurement-experimentation/`, `P08-brand-data-integration/`), by a reviewer who did not author any of them. Read against the portfolio-level documents (`02-epics/EPIC_MAP.md`, `DEPENDENCY_GRAPH.md`, `AUDIT_TO_BACKLOG_TRACEABILITY.md`, `08-risks/PORTFOLIO_RISK_REGISTER.md`, `PORTFOLIO_ANTI_OVERENGINEERING.md`) for consistency. Each package's `04-architecture/`, `07-feasibility/`, `08-reliability/SECURITY.md`, `10-roadmap/`, `11-critique/`, and `99-final/` folders were read in full; other folders were spot-checked as needed.

## Part 1 — Cross-project consistency review

### 1. Product/variant/SKU identity — no conflict found

P01 and P02 never reason about brand-supplied `sku`/`barcode` semantics at all. Their entire ranking/recommendation logic operates on Renivet-internal `products.id` (RAG candidate IDs, `priorityProductIds`, `getAdvancedRecommendations(productId)`). Neither package's `06-data/DATA_CONTRACTS.md` mentions `sku` or `barcode` as an identity mechanism (confirmed by direct grep — zero hits in either file).

P08 defines a separate, brand-ingestion-layer identity model: `sku` (nullable, non-unique, brand-scoped, exact-string-equality match today), `barcode` (present on both `products`/`productVariants` but unused by any matching code), and `nativeSku` (system-generated, unique, explicitly *not* usable as an external mapping target). P08's V1 identity contract is exact-match-only (`sku` OR `barcode` OR normalized-title+full-variant-attributes), with no `brand_external_identifiers` table until Phase 2 (gated on "a brand has two concurrent live sources").

**Verdict: ACCEPT — no conflict.** These are different layers (P08 governs how brand-supplied data gets *mapped onto* a `products.id`; P01/P02 consume `products.id` after that mapping already happened) and neither package assumes the other's identity model. No package assumes a single canonical brand-facing SKU exists today, which is correct — it doesn't.

### 2. Media model — no conflict, actively compatible

P01's `requireMedia` filter (REN-155) depends on `products.media` resolving to valid URLs via `brandMediaItems` through Redis (`mediaCache`). P08's media plan (`04-architecture/COMPONENT_ARCHITECTURE.md`, `06-data/DATA_REQUIREMENTS.md`) is explicit: "**Reuse `brandMediaItems` for File-First media writes; do not perpetuate `productVariants.image`'s raw-URL bypass in new code.**" P08 does not restructure the media table or change how `products.media` resolves — it only adds a second, correctly-behaved writer into the existing structure.

**Verdict: ACCEPT — no conflict; a genuine alignment.** If anything, P08 shipping first would slightly *improve* P01's `requireMedia` reliability (fewer raw-URL-bypass rows) rather than threaten it.

### 3. Event/identity definitions (P05 guest checkout vs. P06 PostHog identity) — real, minor, unaddressed gap

P06's server-side event model (`05-algorithms/CURRENT_ALGORITHM.md`) states plainly: "Server-side capture uses `distinctId: userId` directly... this assumes the caller is already authenticated (cart routes require a logged-in user), so there is no anonymous-merge concern server-side." REN-131 (server-side `purchase_completed` capture, P06 V1 scope) will presumably be built on this same assumption.

P05's REN-95 (guest checkout, "GO WITH CONDITIONS," blocked on 6 decisions, not yet scheduled) would — if and when it ships — create orders with no Clerk `userId`. Both P05's and P06's own `DEPENDENCIES.md` files correctly cross-reference each other for the *already-scheduled* REN-144 (event timing/completeness should be re-validated once REN-144 ships) — this specific cross-reference is done well. But neither package flags that REN-131's server-side capture design will need an anonymous/guest-`distinctId` path once REN-95 ships. This is a forward-looking gap, not a present contradiction, since REN-95 isn't scheduled.

**Verdict: ACCEPT WITH CONDITIONS.** Not a defect in either package as written — both are correct about *today's* system, where checkout requires authentication. Flag as a note for whoever eventually schedules REN-131 alongside REN-95: server-side purchase capture must be designed to accept a non-authenticated distinct ID, or explicitly punt guest-order capture to client-side only.

### 4. Duplicate infrastructure proposals (shared ML host, REN-146/147/151/160) — no conflict, good coordination discipline

P01 (REN-146: add timeouts to all 5 call sites, fix hardcoded-IP config) and P02 (REN-147: independent fallback for cart cross-sell; REN-160: cache `getAdvancedRecommendations`) both touch the same shared files (`sematic-search.ts`, `product-recommendation.ts`) on the same host (`64.227.137.174:8000`). Neither proposes a competing abstraction:
- P01 explicitly considered and *rejected* mandating a shared HTTP-client wrapper across both Epics' files, keeping it "a recommendation, not a requirement... to avoid expanding this Epic's blast radius into P02's territory without coordination" (`11-critique/ARCHITECTURE_CRITIQUE.md`, restated in `ANTI_OVERENGINEERING_REVIEW.md`).
- P02 explicitly names the same coordination need from its side: "Coordination with whoever picks up P01's REN-146... before shipping REN-147/160's changes to those shared files, to avoid conflicting edits" (`07-feasibility/RESOURCE_ASSESSMENT.md`, `04-architecture/INTEGRATIONS.md`).

**Verdict: ACCEPT — no conflict**, but this is the strongest candidate for a concrete pre-execution action item (see closing summary) — both sides correctly *identified* the coordination need but neither assigns who sequences first or how a merge conflict on these two files gets resolved.

### 5. Incompatible metrics/success criteria (P01/P02 logging vs. P06 measurement) — no conflict

P06's own `DEPENDENCIES.md` states plainly: "P01 — REN-154 (search click/result-count logging is a no-op stub) blocks P06 from measuring search quality; owned by P01, cited not duplicated," and the same for P02's REN-160/165. P01/P02 correctly do not attempt to build their own measurement/success-metrics layer for this — `09-validation/SUCCESS_METRICS.md` in both packages defers cross-Epic conversion measurement to P06. Directionally consistent, no circular or contradictory assumption.

**Verdict: ACCEPT — no conflict.**

### 6. Duplicated experimentation infrastructure — none found

Checked all three plausible sites:
- P01: "No A/B experimentation is proposed... these are deterministic correctness fixes, not hypotheses" (`99-final/SRS.md`).
- P02: `09-validation/EXPERIMENT_STRATEGY.md` proposes a phased, cheap-first *verification* process for REN-165 only (desk research → optional survey → only-if-inconclusive instrumented pilot), explicitly not a framework, and explicitly declines to build one ("A full A/B testing framework build-out for REN-165... premature," `11-critique/ANTI_OVERENGINEERING_REVIEW.md`).
- P06 (the Epic literally named "...& Experimentation"): "This Epic is a correctness-fix Epic, not an A/B-testable feature... No formal A/B test needed" (`09-validation/EXPERIMENT_STRATEGY.md`).

**Verdict: ACCEPT — no conflict; matches portfolio expectation exactly.** No package proposes building experimentation infrastructure, consistent with `PORTFOLIO_ANTI_OVERENGINEERING.md`'s expectation that none currently exists and none should be independently invented.

### 7. Unnecessary microservices — none found

No package proposes a new service, model-serving layer, AI gateway, or MCP integration once you see the sibling packages. P02's `BUILD_REUSE_BUY_SIMPLIFY.md` explicitly states "Not applicable" for MCP; P08's `07-feasibility/FEASIBILITY_ASSESSMENT.md` does the same for the batch-file-import problem. P08's AI-assist work is scoped to hosted-LLM API calls (no dedicated inference infra), consistent with `AI_GOVERNANCE.md` principle 2.

**Verdict: ACCEPT — no conflict.**

## Part 2 — The 15-question adversarial pass

**1. Are we solving actual problems?** — **ACCEPT.** Every `FUNCTIONAL_REQUIREMENTS.md` item across all 5 packages traces to a named Linear issue and/or research finding with file:line citations (e.g., P01's FR-1 through FR-10 map 1:1 to REN-146/148/149/151/154/155/156/158/159/167; P08's FR-1 through FR-17 trace to specific research-wave documents). No invented requirement was found in any package.

**2. Are we inventing user stories?** — **ACCEPT.** All 5 packages explicitly separate real user/business capability from engineering tasks, and P01/P02 include an explicit "explicitly not written as stories" / "explicitly rejected story shapes" section calibrating the boundary (e.g., P01 correctly excludes "As a developer, I want a request timeout..." from `USER_STORIES.md`, routing it to `FUNCTIONAL_REQUIREMENTS.md` instead). One borderline case: P02's US-4 ("I want recommendation panels to load quickly") is self-flagged in the same document as "an engineering/performance story with a shopper-visible latency benefit, not a new user-facing capability" — the package is honest about the border case rather than smuggling it through, so this is not counted as a violation.

**3. Are we overengineering?** — **ACCEPT.** Each package's `ANTI_OVERENGINEERING_REVIEW.md` names specific real temptations and explains why each was rejected (circuit breaker for REN-146, batch-precompute job for REN-160, unified recommendation microservice, saga/distributed-transaction framework for REN-144, full reconciliation spine for P08, GA4 build without a decision). Cross-checked against the portfolio-level `PORTFOLIO_ANTI_OVERENGINEERING.md` — the individual packages' self-critiques are consistent with, not looser than, the portfolio-level standard.

**4. Are we copying competitors without evidence?** — **ACCEPT.** No package references a competitor feature as justification anywhere in the requirements/architecture files read. P08's research explicitly rejected "replicate Unicommerce" framing in favor of solving Renivet's own evidenced problem — the one place this temptation plausibly existed, and it was already resisted upstream of this package.

**5. Are we introducing unnecessary AI?** — **ACCEPT.** P08's AI-assist scope (schema-mapping suggestions, attribute normalization) remains human-confirmed-before-first-use (FR-5) and suggest-only for identity matching (FR-11: "No fuzzy/AI-assisted match writes automatically at any confidence level"). The SRS explicitly documents the corrected history: a prior design that let "corroborated fuzzy" SKU matches auto-apply was caught by the research's own critic pass as contradicting its hard guardrail, and the corrected exact-match-only rule is what ships in this package's V1 and V3 gating (`VERSION_TRIGGERS.md`: SKU-matching AI auto-apply requires real match data AND shipped provenance AND enforced `brand_external_identifiers` pinning — three preconditions, not a date). No drift back toward auto-apply was found anywhere in this package.

**6. Are we introducing unnecessary infrastructure?** — **ACCEPT.** Cross-referenced with Part 1 findings #4, #6, #7 above — no case found.

**7. Are we underestimating operations?** — **ACCEPT WITH CONDITIONS.** The underlying operational gaps are real (P08: nobody currently owns manual-mapping-review-queue escalation, characterized in the underlying research as "a dead end dressed up as a feature"; P05: REN-95's "6 decisions" live in a file the package itself flags is empty of the actual enumerated decisions — "this is itself a gap... whoever picks up REN-95 next should locate and read that pilot run's actual decision list"). Condition: both gaps are *honestly disclosed as open* rather than silently assumed staffed — P08's GO_NO_GO makes the staffing decision an explicit condition for GO, and portfolio-level `DECISION_QUEUE.md` (DECISION-XC-003) tracks the AI-review-ownership question. Accept the disclosure; the underlying gap itself still needs a human answer before either P08 V1 or REN-95 runs at real volume.

**8. Are we assuming unavailable data?** — **ACCEPT.** UNKNOWNs are consistently tagged and not laundered into a firm verdict. P01's SRS "HOW MUCH" section states plainly "No cost model or numeric latency/conversion target exists (UNKNOWN)" without asserting a target elsewhere. P08's brand-tier-distribution UNKNOWN is listed as a named GO-WITH-CONDITIONS item in `GO_NO_GO.md` ("the single most load-bearing unmeasured input in the entire research program... remains unmeasured"), not treated as known anywhere else in the package. P06's SRS §7 explicitly keeps "REN-145 historical/full-period runtime impact: PROBABLE, not CONFIRMED" separate from the source-level CONFIRMED findings.

**9. Are we confusing source-confirmed with runtime-confirmed?** — **ACCEPT.** This is the strongest-held discipline across the portfolio. P06's REN-145 CONFIRMED/PROBABLE split survives verbatim into its SRS (§7: "REN-145 currency-unit defect: CONFIRMED at the source-code level"; "historical/full-period runtime impact... PROBABLE, not CONFIRMED"). Spot-checked three other CONFIRMED claims: P01's Subsystem A/B/C descriptions cite exact file:line and quote the actual guard logic (`shouldApplySearchRelevanceOrdering()`); P05's REN-144 order-creation-loop description cites exact line numbers and quotes the actual `catch`-block comment; P08 explicitly re-verified F10 and the `xlsx` version *against live source on 2026-08-30*, distinguishing this from merely restating the original 2026-08 research ("Still present," "Still `^0.18.5` — unchanged"). All three were genuine code reads, not assumptions dressed as confirmation.

**10. Can an existing component do the job?** — **ACCEPT.** `BUILD_REUSE_BUY_SIMPLIFY.md` verdicts consistently favor reuse where evidence supports it: P02's REN-147 verdict is "REUSE — Port Placement B's existing, working fallback chain pattern to Placement A. No build of new fallback logic from scratch" — a direct, evidence-backed reuse call, not a default. P01 reuses `axios`/`fetch`/Redis (`mediaCache` pattern) throughout. P08's whole V1 architecture is explicitly "generalize `products.inventorySource`" and "extend `product-import.tsx`," not new build.

**11. Are dependencies correctly ordered?** — **ACCEPT.** Checked V1 sequencing across all 5 against `DEPENDENCY_GRAPH.md`'s real edges. P06 does not assume P05's REN-144 is done — its `DEPENDENCIES.md` explicitly names it as something to "coordinate... do not let them regress each other" and flags re-validation once REN-144 ships (future tense, correctly ordered). P06 correctly treats REN-154 (P01) and REN-160/165 (P02) as blocking inputs it does not itself build. No package was found assuming another Epic's unshipped V1 work as a precondition for its own V1.

**12. Is any Epic not mature enough to implement?** — **ACCEPT.** P08's `GO_NO_GO.md` gives "GO WITH CONDITIONS, pending a Renivet greenlight decision to convert this package into tracked Linear work" — not an unconditional GO — and states the zero-Linear-tracking fact plainly rather than treating 16 waves of research as itself sufficient authorization. It explicitly explains why this isn't relabeled "POC required" (the design work is genuinely further along than that) without overstating readiness for engineering to simply start.

**13. Are V2/V3 items properly trigger-gated?** — **ACCEPT.** Spot-checked P01 (typo tolerance gated on REN-146 fallback-activation data with an explicit "DECISION REQUIRED" on what threshold counts as meaningful, not a vague "later"), P02 (REN-168 gated on "demonstrated business need," REN-165 gated on Phase-1-verification outcome), P05 (order-then-pay gated on "partial-order incidents continu[ing] post-V1.1 at a non-trivial rate," measured against production incident data), P08 (5-item trigger table, all named observable events — "a second, named, API-capable brand is actually onboarding," not a date — with an explicit instruction not to invent dates). No vague "later" dressed as a trigger was found in any spot-check.

**14. Is the design feasible for the current team/resources?** — **ACCEPT WITH CONDITIONS.** `RESOURCE_ASSESSMENT.md` files consistently avoid asserting an unevidenced specialist role: P01 explicitly states an ML/data-science specialist is "NOT NEEDED for this Epic"; P02 needs no new specialist beyond a content/copy reviewer; P08 needs no dedicated ML engineer (bounded hosted-LLM API cost, "Claude Haiku 4.5 class pricing," no GPU/inference infra). The one real gap is P05's REN-95, honestly labeled "XL — largest single item in the reconciled portfolio," requiring "product/security/finance sign-off first" without a named individual — but this is explicitly deferred to the (currently unenumerated, see finding #7) decision queue rather than assumed resolved. Condition: this sign-off capacity needs to actually exist before REN-95 is scheduled, and no package confirms it does.

**15. What is the simplest version that gets the business result?** — **Synthesis judgment.** The most over-scoped V1 candidate across the portfolio is arguably P08's (17 functional requirements, a new `import_batches`/`import_records` schema, two AI-assist use cases, plus an independent F10 security fix) — but this is defensible, not overengineering: it is explicitly the smallest option surviving a 16-wave research program's own anti-overengineering pass, gated behind a leadership-authorization decision rather than silently assumed approved, and its own package flags where it added *explanatory* depth beyond the research without expanding the *build* itself. If anything is trimmable pre-execution, it's sequencing — F10 should ship standalone, immediately, decoupled from the rest of P08's V1 authorization decision, which the package itself already recommends. The best example of appropriately minimal scoping is **P01**: nine small, independently-shippable, zero-new-infrastructure fixes, three real user stories out of ten items (the rest correctly left as engineering requirements), and one explicitly deferred item (typo tolerance) with a concrete data-based trigger rather than a schedule slot.

## Closing summary

**Most important cross-project fix needed before execution:** Assign explicit ownership and sequencing for the two files P01 (REN-146) and P02 (REN-147, REN-160) will both edit — `src/lib/python/sematic-search.ts` and `src/lib/python/product-recommendation.ts`. Both packages independently identified this exact coordination need and both correctly declined to force a shared abstraction as a requirement, but neither assigns who goes first or how a merge conflict is resolved if both Epics are scheduled concurrently. This is a five-minute planning decision, not new design work, but it is the one concrete, actionable gap this pass found between otherwise well-coordinated packages.

**Overall verdict:** The 5 packages are internally consistent to an unusual degree for independently-authored SRS-grade documents — no contradiction was found on product/variant identity, media model, event/identity semantics, or infrastructure duplication, and the two real gaps found (the future P05-guest-checkout/P06-identity interaction, and the unresolved REN-95/P08 staffing questions) are both already honestly disclosed as open within the packages themselves rather than papered over. The CONFIRMED/INFERRED/UNKNOWN/DECISION-REQUIRED discipline and the "do not launder a PROBABLE into a CONFIRMED" rule both held up under spot-checking. **This set is ready to proceed to an execution-readiness precheck**, conditional on resolving the one concrete coordination item above and carrying forward (not silently dropping) the staffing/decision-queue gaps already named in each package's own `OPEN_DECISIONS.md`/`GO_NO_GO.md`.
