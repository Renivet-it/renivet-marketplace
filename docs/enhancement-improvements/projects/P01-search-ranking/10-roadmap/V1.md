# V1 — P01

## Scope: ship the existing backlog fixes as the minimum valuable, safe capability

V1 = REN-146, REN-148 (staged step), REN-149, REN-151, REN-154, REN-155, REN-156, REN-158, REN-159. This is not a phased subset — it is the entire active backlog, because every item is independently small, independently valuable, and none requires a capability that doesn't already exist (per `07-feasibility/FEASIBILITY_ASSESSMENT.md`). There is no reason to hold any of these back to a later version.

## Recommended sequencing (not a hard dependency chain — see `07-feasibility/DEPENDENCIES.md`)

1. **REN-146** first — highest leverage (shared with P02, closes the one true reliability gap), and touches the smallest, most isolated code (HTTP client config).
2. **REN-149** — isolated, client-only, zero risk to server-side search logic.
3. **REN-155**, then **REN-154** — count correctness before count logging, so REN-154 doesn't log a number about to change.
4. **REN-158**, then **REN-159** — cache the query shape after its WHERE-clause construction has already settled.
5. **REN-151** — can happen any time; recommend after REN-158 to minimize simultaneous changes to the same function's control flow.
6. **REN-156** — anytime, zero-risk deletion.
7. **REN-148** — independent of the above; primarily a scheduling/process decision, can run in parallel with all the code changes.
