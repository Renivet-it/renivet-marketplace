# Architecture Critique — P02

## What's wrong with the current architecture (beyond the six tracked issues)

1. **No shared recommendation service abstraction**, despite Placements A and B calling the identical underlying function. This isn't itself a tracked defect, but it's why REN-147's fallback divergence between A and B was able to happen unnoticed — there's no single place where "how does cart cross-sell degrade" and "how does PDP degrade" are forced to be consistent. Fixing REN-147 by porting B's pattern to A (as this package recommends) treats the symptom without addressing why two call sites implementing the same capability were allowed to diverge in resilience posture. **This package does not recommend building a shared service now** (that would be scope creep beyond four confirmed bugs — see `ANTI_OVERENGINEERING_REVIEW.md`), but flags it as a legitimate medium-term architectural improvement if a third ML-dependent recommendation surface is ever added.
2. **`getShopRecommendations` (tRPC procedure) appears to be dead code relative to the shop page's actual SSR path**, which calls `recommendationQueries` directly (`04-architecture/COMPONENT_ARCHITECTURE.md`). This is either an unused procedure (worth confirming with the original author/removing if truly unused) or is consumed by some other client-side caller not covered in this pass's search — **UNKNOWN**, worth a quick grep-for-callers check before REN-160 implementation begins, so caching effort isn't misapplied to the wrong code path.
3. **Hardcoded external host, twice, with dead config plumbing around it** (`01-research/EVIDENCE_INDEX.md` #1) is a code-quality smell independent of REN-147's resilience concern — it suggests the `EMBEDDING_SERVICE_URL` env var was introduced with good intent (presumably to support local/staging vs. production hosts) and then bypassed, possibly during a debugging session, without being restored. This is exactly the kind of drift that formal architecture documentation (which does not exist for this Epic, per `04-architecture/SYSTEM_ARCHITECTURE.md`) would normally catch in review.

## What's right and should be preserved

- Placement C's multi-signal Postgres scorer (`recommendationQueries`) is a well-structured, reasonably sophisticated piece of first-party logic with sensible time-decay windows and graceful multi-tier fallback (order → merged → platform defaults) — its *architecture* is sound; only its *consumption* (REN-150) is broken. Any future rework should build on this, not replace it.
- Placement B's frontend cascading-fallback pattern is a clean, testable use of react-query's `enabled` flag chaining — genuinely good code worth using as a template (per FR-1).
